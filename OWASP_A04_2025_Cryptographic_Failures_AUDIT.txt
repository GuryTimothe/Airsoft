Audit OWASP A04:2025 - Cryptographic Failures
Date: 2026-07-18
Perimetre: backend Symfony/API Platform + frontend Next.js + infra compose

Reference:
https://owasp.org/Top10/2025/A04_2025-Cryptographic_Failures/

==================================================
1) CE QUE TU AS (OK)
==================================================

[OK] Hashing des mots de passe via mecanisme Symfony moderne
- password_hashers configure sur PasswordAuthenticatedUserInterface avec "auto".
- En pratique: algo adaptatif (bcrypt/argon selon plateforme Symfony/PHP).
- Fichier:
  - backend/config/packages/security.yaml

[OK] Politique mot de passe minimale au niveau applicatif
- Longueur min 12 + complexite (maj/min/chiffre/symbole).
- Fichier:
  - backend/src/Entity/User.php

[OK] Gestion des cles JWT hors code source
- secret/public key + passphrase injectes via variables d'environnement.
- Fichier:
  - backend/config/packages/lexik_jwt_authentication.yaml

[OK] Validation defensive des JWT
- Verification claims iss/aud.
- Verification signature metier pwd_sig et nonce de revocation.
- Invalidations explicites si payload incomplet/mismatch.
- Fichier:
  - backend/src/Security/Jwt/TokenVersionSubscriber.php

[OK] Generation d'identifiants/token cryptographiquement aleatoires
- random_bytes utilise pour jti JWT et nonce utilisateur.
- Fichiers:
  - backend/src/Security/Jwt/TokenVersionSubscriber.php
  - backend/src/Security/Jwt/JwtRevocationStore.php
  - backend/src/Security/Jwt/LoginCsrfManager.php

[OK] Cookie d'auth durci partiellement
- httpOnly=true, sameSite=Lax.
- Fichier:
  - backend/src/Security/Jwt/JwtCookieManager.php

[OK] Tests unitaires crypto/JWT presents
- Tests TokenVersionSubscriber et JwtRevocationStore.
- Fichiers:
  - backend/tests/Security/Jwt/TokenVersionSubscriberTest.php
  - backend/tests/Security/Jwt/JwtRevocationStoreTest.php

==================================================
2) CE QUE TU N'AS PAS OU A RENFORCER
==================================================

[MANQUANT] Enforcement HTTPS/HSTS visible au niveau app/reverse proxy du repo
- OWASP A04 recommande TLS fort + HSTS.
- Je ne vois pas de configuration HSTS/security headers explicites ici.
- Impact: risque de downgrade/transport non force selon infra.

[PARTIEL] Cookie secure conditionnel
- Le flag secure du cookie depend de request->isSecure().
- En HTTP/dev il reste false (normal en dev), mais en prod il faut garantir HTTPS partout pour ne jamais emettre de cookie non-secure.
- Fichier:
  - backend/src/Security/Jwt/JwtCookieManager.php

[PARTIEL] Duree de vie JWT non explicite dans le fichier bundle
- token_ttl n'est pas defini explicitement dans la config (default bundle probable).
- OWASP recommande une politique explicite de duree de vie + rotation.
- Fichier:
  - backend/config/packages/lexik_jwt_authentication.yaml

[MANQUANT] Chiffrement des donnees sensibles au repos (application-level)
- Aucune preuve de chiffrement applicatif de champs sensibles en base (PII, etc.).
- A valider/traiter selon classification des donnees et exigences legales.

[MANQUANT] Gestion avancee des cles (rotation KMS/HSM)
- Les cles sont externalisees via env (bien), mais pas de preuve d'un KMS/HSM ni procedure de rotation formalisee dans ce repo.

[PARTIEL] Controle cache des reponses sensibles
- OWASP A04 recommande des directives explicites anti-cache sur donnees sensibles.
- Je ne vois pas de politique globale Cache-Control/Pragma appliquee sur endpoints sensibles.

==================================================
3) VERDICT RAPIDE
==================================================

Niveau actuel sur A04: BON sur la base applicative (hash/JWT/randomness), mais incomplet sur le hardening crypto infra.

Points forts:
- hashing moderne + politique de mot de passe
- JWT avec validations supplementaires
- random_bytes correctement utilise
- tests crypto presents

Gaps principaux:
- enforcement HTTPS/HSTS non visible
- politique JWT TTL non explicite
- chiffrement au repos non etabli
- gouvernance de rotation/stockage de cles a formaliser

==================================================
4) PRIORITES CONSEILLEES (ordre)
==================================================

1. Forcer HTTPS partout en prod + activer HSTS (reverse proxy/ingress).
2. Definir explicitement token_ttl et documenter la politique de rotation/revocation.
3. Ajouter une politique cache stricte pour endpoints sensibles (no-store/no-cache selon besoin).
4. Classifier les donnees sensibles et chiffrer au repos ce qui doit l'etre (DB/KMS/app-level).
5. Formaliser une procedure de gestion de cles (generation, rotation, revocation, stockage KMS/HSM).
