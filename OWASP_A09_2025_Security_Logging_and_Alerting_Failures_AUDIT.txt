==================================================
2) CE QUE TU N'AS PAS OU A RENFORCER
==================================================

[MANQUANT] Configuration de logging securite explicite dans le backend
- Pas de configuration Monolog dediee trouvee dans backend/config/packages.
- Pas de strategie visible de format, retention, rotation, correlation IDs, redaction PII.

[MANQUANT] Journalisation applicative des evenements securite
- Pas d'usage explicite de LoggerInterface dans backend/src.
- Donc pas de traces metier securite codees pour:
  - echecs d'authentification (avec contexte utile)
  - acces refuses (authorization denied)
  - actions admin sensibles (exports, changements roles/settings)
  - anomalies metier (patterns suspects)

[MANQUANT] Alerting operationnel
- Pas de pipeline d'alerting (SIEM, webhook, email, Slack, PagerDuty) visible.
- Pas de seuils d'alerte documentes (bruteforce, 401/403/429 burst, erreurs 5xx, actions admin anormales).

[MANQUANT] Centralisation et protection d'integrite des logs
- Pas de preuve de centralisation (ELK/OpenSearch/SaaS observability).
- Pas de mecanisme visible d'immutabilite/tamper-evidence des logs applicatifs.

[PARTIEL] Cas de test orientes detection/alerte
- Les tests securite existent sur les controles, mais pas de tests verifies "event logged + alert raised".
- OWASP A09 recommande de verifier que les attaques detectees declenchent une alerte exploitable.

[PARTIEL] Gouvernance de reponse a incident
- Checklists deployment/qualite presentes, mais playbooks d'escalade A09 peu formalises (qui alerte qui, sous quel delai, que faire).

3) VERDICT RAPIDE
==================================================

Niveau actuel sur A09: FAIBLE a INTERMEDIAIRE.

Forces:
- controles securite applicatifs deja solides
- codes d'erreur securite coherents
- base documentaire qui identifie les besoins

Gaps majeurs:
- peu/pas de logs securite applicatifs explicites
- pas d'alerting operationnel connecte
- pas de centralisation/integrite formelle des journaux

==================================================
4) PRIORITES CONSEILLEES (ordre)
==================================================

1. Ajouter une politique de security logging (schema d'evenements, champs obligatoires, redaction PII, retention).
2. Implementer LoggerInterface sur les points critiques: login fail, access denied, actions admin, changements de role, erreurs JWT/revocation.
3. Configurer une stack de centralisation/monitoring (ex: ELK/OpenSearch/SaaS) avec correlation et recherche.
4. Definir des alertes actionnables (seuils 401/403/429/5xx, bruteforce, anomalies admin) + canal d'escalade.
5. Ecrire des tests d'observabilite securite (verification qu'un evenement critique produit un log et declenche l'alerte attendue).
6. Documenter un playbook incident A09 (triage, owner, SLA, post-mortem).
